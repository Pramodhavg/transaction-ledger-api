# Assumptions

These are the interpretations made wherever the spec left room, and why each one was chosen.

## Identifiers and data
1. **IDs are UUIDs generated by the server** (v4). They are hard to guess, don't reveal how many records exist, and can be generated before insert. Transfer leg references need the transfer id up front. A malformed id returns `400 INVALID_ACCOUNT_ID`, and a well-formed but unknown id returns `404 ACCOUNT_NOT_FOUND`.
2. **Account names are not unique.** Two holders can share a name. Names are trimmed and must be 1–100 characters.
3. **Only `name` is accepted when creating an account.** Sending `balance`, `id`, `created_at` or any unknown field is **rejected** with `400`, not silently ignored, so a client bug that tries to set a balance is noticed immediately. Unknown fields are rejected on every endpoint.
4. **Accounts can't be updated or deleted.** The spec defines no such operations. Foreign keys use `ON DELETE RESTRICT`, so an account with ledger history can never be removed by accident.
5. **Timestamps are UTC** and returned in ISO-8601. A transaction's `created_at` is the moment its row was written, taken with `clock_timestamp()` after the account lock is held. So "latest first" matches the order balances actually changed.

## Money
6. **Single currency with 2 decimal places.** There is no multi-currency support or FX.
7. **`amount` may be a JSON number or a string.** It must be `> 0` and have at most 2 decimals. More decimals are **rejected, not rounded**, because silently changing an amount is worse than refusing it. `NaN`, `Infinity`, booleans and empty strings are rejected.
8. **Per-transaction maximum of `1,000,000,000.00`.** This is a sanity cap against typos and abuse, applied to transactions and transfers.
9. **Maximum balance of `9,999,999,999,999,999.99`**, the largest value `NUMERIC(18,2)` can store. A credit that would exceed it returns `422 BALANCE_LIMIT_EXCEEDED`. The API checks this before writing, and if Postgres ever reports a numeric overflow anyway, that is mapped to the same `422` instead of a `500`.
10. **Money is returned as a string** with exactly two decimals (`"150.00"`). JSON numbers are parsed as binary floats by many clients (JavaScript included), which would silently lose precision. Internally money is `Decimal` in Python and `NUMERIC(18,2)` in Postgres, never float.

## Transactions
11. **Rejected or failed transactions are not stored.** The ledger contains only entries that changed a balance. An insufficient-balance debit leaves no trace, and its `reference_id` stays free to reuse. A separate audit log of attempts would be a reasonable extension.
12. **A duplicate `reference_id` returns `409 DUPLICATE_TRANSACTION` with the original transaction in `details.transaction`.** Nothing is written and the balance doesn't change. This makes retries after a network timeout safe: the client learns the outcome of its first attempt.
13. **The payload of a duplicate is not compared.** A retry with a different amount still returns the original. The `reference_id` is the identity of the operation. (A stricter design could return a different error when the payload differs.)
14. **The duplicate check runs before the balance check.** Retrying a debit that already succeeded returns `409` ("already done"), not a misleading `422`.
15. **`reference_id` is trimmed, case-sensitive and 1–100 characters**, and unique per account. Other accounts may reuse it. The prefix `transfer:` is reserved for transfer legs and rejected in client requests.
16. **`description` is optional**: trimmed, up to 255 characters, `null` when omitted.
17. **"Balance must equal the result of all valid transactions"** is enforced by updating the stored balance in the same DB transaction as the ledger insert. It is verified by tests that reconcile every account after every test case. Each row also stores `balance_after`, so the history can be audited and replayed.

## Immutability
18. **Ledger rows can't be changed or deleted.** The API has no such endpoints (`405`/`404`), and a Postgres trigger rejects any `UPDATE` or `DELETE` on `transactions` and `transfers`, even from raw SQL. Corrections would be made with new compensating entries, as in accounting.
19. **`TRUNCATE` is not blocked by the trigger.** It's an administrative operation, not something the application does, and the test suite uses it to reset its own database. In production the application's database role would also not be granted `UPDATE`, `DELETE` or `TRUNCATE` on ledger tables.

## History and pagination
20. **An unknown account returns `404`, not an empty list**, so typos in the id are visible.
21. **`page` ≥ 1 (default 1) and `limit` from 1 to 100 (default 20).** Out-of-range or non-integer values return `400 INVALID_PAGINATION` and are not silently clamped, so the client gets exactly what it asked for or a clear error.
22. **A page past the end returns `200` with an empty `data` list** and accurate metadata. It isn't an error: the collection exists, there's just nothing on that page.
23. **`page_size` is the requested `limit`**, not the number of items on that page. `total_pages` is `0` when there are no records.
24. **Sort order is `created_at DESC, id DESC`.** The `id` tiebreaker keeps the order deterministic when timestamps are equal, so paging never repeats or skips a row.
25. **The type filter is exact and lowercase** (`credit`, `debit`). Omitting it returns both types.

## Transfers
26. **A transfer is a transfer record plus two ordinary ledger entries**: a debit on the source and a credit on the destination, linked by `transfer_id`. Their references are `transfer:<transfer_id>:debit` and `transfer:<transfer_id>:credit`, which can never collide with client references. They appear in each account's history like any other transaction.
27. **Transfer `reference_id` is unique per source account** and lives in its own namespace, separate from transaction references.
28. **Same-account transfers are rejected** with `400 SAME_ACCOUNT_TRANSFER` (also enforced by a database CHECK constraint).
29. **The transfer `description` is copied onto both ledger entries.** Without one, the entries read `Transfer to <id>` and `Transfer from <id>`.

## Status codes
30. **`400`** means the request itself is invalid (FastAPI's default `422` for validation is replaced). **`404`** means not found. **`409`** means already processed (duplicate reference). **`422`** means a valid request refused by a business rule (insufficient balance, balance limit). **`405`** means wrong method. **`500`** is a generic unexpected error with no internals exposed. **`503`** means the database is unreachable (health check).

## Scope and operations
31. **No authentication, authorization, rate limiting or multi-tenancy.** These were out of scope for the assignment.
32. **Migrations run automatically when the API starts**, so the project works with one command. In production they would run as a separate release step, so several replicas never migrate at once.
33. **The database credentials in `docker-compose.yml` are local development defaults** and can be overridden via `.env`. They aren't secrets.
34. **Single database instance.** Concurrency control uses Postgres row locks at the default `READ COMMITTED` isolation level. History reads use one `REPEATABLE READ` snapshot so the total count and the page agree.
