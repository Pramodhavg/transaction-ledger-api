# API Reference

**Base URL:** `http://localhost:8000/api/v1`

**Interactive docs:** the same contract is available as [Swagger UI](http://localhost:8000/docs) (try every endpoint in the browser), [ReDoc](http://localhost:8000/redoc) and raw OpenAPI at [`/openapi.json`](http://localhost:8000/openapi.json). Postman can import that URL directly (Import → Link).

## Conventions

| Topic | Rule |
|---|---|
| **Format** | JSON request and response bodies (`Content-Type: application/json`). |
| **IDs** | UUIDs generated by the server. A malformed id returns `400 INVALID_ACCOUNT_ID`. |
| **Money in** | `amount` may be a JSON number (`100`, `10.5`) or a string (`"100.00"`). It must be `> 0` and `≤ 1000000000.00`, with at most 2 decimal places. Extra decimals are **rejected, never rounded**. |
| **Money out** | Always a string with exactly two decimals: `"150.00"`. JSON numbers are parsed as binary floats by many clients (JavaScript included), so strings avoid any precision loss. |
| **Timestamps** | ISO-8601 in UTC, e.g. `"2026-10-26T09:30:00.123456Z"`. |
| **Unknown fields** | Rejected with `400 VALIDATION_ERROR` on every request body. A client can never set `id`, `balance`, `balance_after` or `created_at`. |
| **Idempotency** | `reference_id` makes writes safe to retry: re-sending it returns `409` with the original record and changes nothing. |
| **Immutability** | Transactions and transfers can't be edited or deleted. No such endpoints exist (`405`/`404`), and the database rejects such changes too. |

## Health

### `GET /health`
Reports whether the API is running and can reach the database.

`200 OK`
```json
{"status": "ok", "database": "ok"}
```
`503 Service Unavailable` with code `SERVICE_UNAVAILABLE` if the database is unreachable.

## Accounts

### `POST /accounts`: create an account

Only `name` may be sent. The `id`, `balance` (always `0.00`) and `created_at` are set by the server.

| Field | Type | Rules |
|---|---|---|
| `name` | string | Required, 1–100 characters after trimming whitespace |

```http
POST /api/v1/accounts
Content-Type: application/json

{"name": "Alice Johnson"}
```

`201 Created`
```json
{
  "id": "8f14e45f-ceea-4f6a-9c1a-2b5d3e7a9c01",
  "name": "Alice Johnson",
  "balance": "0.00",
  "created_at": "2026-10-26T09:30:00.123456Z"
}
```

| Error | When |
|---|---|
| `400 VALIDATION_ERROR` | `name` is missing, blank, too long or not a string, or the client sent `balance`, `id`, `created_at` or any other field |

Example: trying to set the balance.
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "balance: Unknown or read-only field; it cannot be set by the client",
    "details": {"errors": [{"field": "balance", "location": "body",
                            "message": "Unknown or read-only field; it cannot be set by the client"}]}
  }
}
```

### `GET /accounts/{account_id}`: account details

`200 OK` returns the same shape as the create response, with the current balance.

| Error | When |
|---|---|
| `400 INVALID_ACCOUNT_ID` | `account_id` is not a valid UUID |
| `404 ACCOUNT_NOT_FOUND` | No account with this id |

### `GET /accounts/{account_id}/balance`: current balance

`200 OK`
```json
{"account_id": "8f14e45f-ceea-4f6a-9c1a-2b5d3e7a9c01", "balance": "150.00"}
```
The balance always equals the sum of all credits minus all debits on the account.

The errors are the same as for `GET /accounts/{account_id}`.

## Transactions

### `POST /accounts/{account_id}/transactions`: credit or debit

| Field | Type | Rules |
|---|---|---|
| `type` | string | Required: `"credit"` (adds) or `"debit"` (subtracts), lowercase |
| `amount` | number or string | Required: `> 0`, `≤ 1000000000.00`, at most 2 decimals |
| `reference_id` | string | Required: 1–100 characters after trimming. Unique per account. Must not start with `transfer:` (reserved for transfer legs). |
| `description` | string | Optional: up to 255 characters, trimmed |

```http
POST /api/v1/accounts/8f14e45f-ceea-4f6a-9c1a-2b5d3e7a9c01/transactions
Content-Type: application/json

{"type": "credit", "amount": "100.00", "reference_id": "deposit-001", "description": "Salary"}
```

`201 Created`
```json
{
  "id": "45c48cce-2e2d-4fbd-9a7b-6c1e2d3f4b03",
  "account_id": "8f14e45f-ceea-4f6a-9c1a-2b5d3e7a9c01",
  "type": "credit",
  "amount": "100.00",
  "description": "Salary",
  "reference_id": "deposit-001",
  "balance_after": "150.00",
  "transfer_id": null,
  "created_at": "2026-10-26T09:30:00.123456Z"
}
```
- `balance_after` is the account balance immediately after this transaction.
- `transfer_id` is set only when the entry is one side of a transfer.

**Behaviour**
- The ledger entry and the balance update are **one atomic operation**: both are committed or neither is.
- Concurrent requests for the same account are serialized with a row lock, so balances can never be lost or overdrawn.
- **Rejected transactions are not stored.** An insufficient-balance debit leaves no trace in the history, and its `reference_id` stays free.
- **Duplicates:** if `reference_id` was already used on this account, nothing is written and the API returns `409` with the **original** transaction, even if the retry has a different amount. The same `reference_id` may be used on other accounts.
- The duplicate check runs before the balance check, so retrying a debit that already succeeded returns `409` ("already done"), not `422`.

| Error | When |
|---|---|
| `400 INVALID_ACCOUNT_ID` | `account_id` in the URL is not a UUID |
| `400 INVALID_TRANSACTION_TYPE` | `type` is missing or not `credit`/`debit` |
| `400 INVALID_AMOUNT` | `amount` is missing, ≤ 0, has more than 2 decimals, exceeds the per-transaction maximum, or isn't a number (`"abc"`, `"NaN"`, `true`, …) |
| `400 VALIDATION_ERROR` | `reference_id` is missing or invalid, unknown fields were sent, the body isn't valid JSON, or several different fields are invalid at once |
| `404 ACCOUNT_NOT_FOUND` | The account doesn't exist |
| `409 DUPLICATE_TRANSACTION` | `reference_id` was already used on this account |
| `422 INSUFFICIENT_BALANCE` | Debit larger than the current balance |
| `422 BALANCE_LIMIT_EXCEEDED` | Credit would take the balance above `9999999999999999.99`, the `NUMERIC(18,2)` maximum |

`409 Conflict`:
```json
{
  "error": {
    "code": "DUPLICATE_TRANSACTION",
    "message": "A transaction with reference_id 'deposit-001' already exists for this account",
    "details": {
      "transaction": {
        "id": "45c48cce-2e2d-4fbd-9a7b-6c1e2d3f4b03",
        "account_id": "8f14e45f-ceea-4f6a-9c1a-2b5d3e7a9c01",
        "type": "credit",
        "amount": "100.00",
        "description": "Salary",
        "reference_id": "deposit-001",
        "balance_after": "150.00",
        "transfer_id": null,
        "created_at": "2026-10-26T09:30:00.123456Z"
      }
    }
  }
}
```

`422 Unprocessable Entity`:
```json
{
  "error": {
    "code": "INSUFFICIENT_BALANCE",
    "message": "Insufficient balance: available 100.00, requested 150.00",
    "details": {"account_id": "8f14e45f-ceea-4f6a-9c1a-2b5d3e7a9c01",
                "balance": "100.00", "requested_amount": "150.00"}
  }
}
```

### `GET /accounts/{account_id}/transactions`: history

| Query parameter | Default | Rules |
|---|---|---|
| `type` | both types | `credit` or `debit` |
| `page` | `1` | Integer ≥ 1 |
| `limit` | `20` | Integer from 1 to 100 |

```http
GET /api/v1/accounts/8f14e45f-ceea-4f6a-9c1a-2b5d3e7a9c01/transactions?type=credit&page=1&limit=20
```

`200 OK`
```json
{
  "data": [
    {
      "id": "45c48cce-2e2d-4fbd-9a7b-6c1e2d3f4b03",
      "account_id": "8f14e45f-ceea-4f6a-9c1a-2b5d3e7a9c01",
      "type": "credit",
      "amount": "100.00",
      "description": "Salary",
      "reference_id": "deposit-001",
      "balance_after": "150.00",
      "transfer_id": null,
      "created_at": "2026-10-26T09:30:00.123456Z"
    }
  ],
  "pagination": {
    "page": 1,
    "page_size": 20,
    "total_records": 42,
    "total_pages": 3,
    "has_next": true,
    "has_previous": false
  }
}
```

**Behaviour**
- Sorted **latest first** by `created_at`, then by `id` as a tiebreaker, so the order is stable across pages and no row is repeated or skipped.
- `page_size` is the requested `limit`. `total_records` and `total_pages` respect the `type` filter. `total_pages` is `0` for an empty history.
- A page past the end returns `200` with `"data": []` and accurate metadata.
- The count and the page are read from one consistent snapshot, so they always agree.
- An unknown account returns `404`, not an empty list.

| Error | When |
|---|---|
| `400 INVALID_ACCOUNT_ID` | `account_id` is not a UUID |
| `400 INVALID_PAGINATION` | `page` < 1, `limit` < 1 or > 100, or either one isn't an integer (values are rejected, not silently clamped) |
| `400 INVALID_TRANSACTION_TYPE` | `type` isn't `credit` or `debit` |
| `400 VALIDATION_ERROR` | Several different parameters are invalid at once |
| `404 ACCOUNT_NOT_FOUND` | The account doesn't exist |

## Transfers

### `POST /transfers`: move money between two accounts

| Field | Type | Rules |
|---|---|---|
| `from_account_id` | UUID | Required, must exist |
| `to_account_id` | UUID | Required, must exist and differ from `from_account_id` |
| `amount` | number or string | Same rules as for transactions |
| `reference_id` | string | Required, 1–100 characters. Unique per **source** account. |
| `description` | string | Optional, up to 255 characters. Copied onto both ledger entries. |

```http
POST /api/v1/transfers
Content-Type: application/json

{
  "from_account_id": "8f14e45f-ceea-4f6a-9c1a-2b5d3e7a9c01",
  "to_account_id": "c9f0f895-fb98-4b9f-8c9b-5a1d2e3f4a02",
  "amount": "30.00",
  "reference_id": "rent-2026-10",
  "description": "October rent"
}
```

`201 Created` (spec example: A = 100, B = 50)
```json
{
  "transfer": {
    "id": "d3d94468-02a4-4e8e-8b1f-7a2b3c4d5e04",
    "from_account_id": "8f14e45f-ceea-4f6a-9c1a-2b5d3e7a9c01",
    "to_account_id": "c9f0f895-fb98-4b9f-8c9b-5a1d2e3f4a02",
    "amount": "30.00",
    "reference_id": "rent-2026-10",
    "description": "October rent",
    "created_at": "2026-10-26T09:30:00.123456Z"
  },
  "from_account": {"account_id": "8f14e45f-ceea-4f6a-9c1a-2b5d3e7a9c01", "balance": "70.00"},
  "to_account": {"account_id": "c9f0f895-fb98-4b9f-8c9b-5a1d2e3f4a02", "balance": "80.00"}
}
```

**Behaviour**
- One database transaction writes the transfer record, a **debit** on the source, a **credit** on the destination, and both balances. Any failure rolls back everything, so a partial transfer is impossible.
- Each side appears in its account's history as a normal transaction with `transfer_id` set and `reference_id` = `transfer:<transfer_id>:debit` or `transfer:<transfer_id>:credit`. Without a description, the entries read `Transfer to <id>` and `Transfer from <id>`.
- Both accounts are locked in a fixed order (sorted by id), so simultaneous opposite transfers (A→B and B→A) can't deadlock.
- Transfer references are a separate namespace from transaction references: a transfer may reuse a `reference_id` that a normal transaction on the same account already uses.

| Error | When |
|---|---|
| `400 INVALID_ACCOUNT_ID` | `from_account_id` or `to_account_id` isn't a UUID |
| `400 INVALID_AMOUNT` | Same rules as for transactions |
| `400 VALIDATION_ERROR` | `reference_id` is missing or invalid, unknown fields were sent, or several fields are invalid |
| `400 SAME_ACCOUNT_TRANSFER` | `from_account_id` equals `to_account_id` |
| `404 ACCOUNT_NOT_FOUND` | Either account doesn't exist (`details.account_id` says which) |
| `409 DUPLICATE_TRANSFER` | `reference_id` was already used for a transfer from this source account. `details.transfer` holds the original. |
| `422 INSUFFICIENT_BALANCE` | The source balance is lower than `amount` |
| `422 BALANCE_LIMIT_EXCEEDED` | The destination balance would exceed `9999999999999999.99` |

## Errors

### Format
Every error, including unknown routes, wrong methods and unexpected server errors, has the same shape:

```json
{"error": {"code": "MACHINE_READABLE_CODE", "message": "Human-readable explanation", "details": {}}}
```
Clients should branch on `code`; `message` is for people. A `500` never includes stack traces, SQL or exception text; those go to the server log only.

### Codes

| HTTP | Code | Meaning |
|---|---|---|
| 400 | `VALIDATION_ERROR` | Invalid request body or parameters (generic, or several fields at once) |
| 400 | `INVALID_ACCOUNT_ID` | An account id isn't a valid UUID |
| 400 | `INVALID_AMOUNT` | `amount` is invalid |
| 400 | `INVALID_TRANSACTION_TYPE` | `type` isn't `credit` or `debit` |
| 400 | `INVALID_PAGINATION` | `page` or `limit` is out of range or not an integer |
| 400 | `SAME_ACCOUNT_TRANSFER` | A transfer's source and destination are the same |
| 404 | `ACCOUNT_NOT_FOUND` | The account doesn't exist |
| 404 | `NOT_FOUND` | No endpoint matches the URL |
| 405 | `METHOD_NOT_ALLOWED` | The endpoint exists, but not for this method. `details.allowed_methods` and the `Allow` header list the valid methods. |
| 409 | `DUPLICATE_TRANSACTION` | `reference_id` already used on this account; `details.transaction` is the original |
| 409 | `DUPLICATE_TRANSFER` | `reference_id` already used for a transfer from this account; `details.transfer` is the original |
| 422 | `INSUFFICIENT_BALANCE` | The debit or transfer exceeds the available balance |
| 422 | `BALANCE_LIMIT_EXCEEDED` | The credit would push the balance past the storable maximum |
| 500 | `INTERNAL_ERROR` | Unexpected server error |
| 503 | `SERVICE_UNAVAILABLE` | The database is unreachable (health check) |

**Why 400 and 422 are split:** FastAPI's default `422` for bad input is replaced, so `400` always means "fix the request" and `422` always means "the request is valid, but a business rule refused it".

### Validation errors
Validation failures list every problem in `details.errors`:

```json
{
  "error": {
    "code": "INVALID_AMOUNT",
    "message": "amount: Decimal input should have no more than 2 decimal places",
    "details": {"errors": [{"field": "amount", "location": "body",
                            "message": "Decimal input should have no more than 2 decimal places"}]}
  }
}
```
- `location` is `body`, `path` or `query`.
- The code is chosen by field: `amount` → `INVALID_AMOUNT`, `type` → `INVALID_TRANSACTION_TYPE`, any account id → `INVALID_ACCOUNT_ID`, `page`/`limit` → `INVALID_PAGINATION`.
- When all errors map to the same specific code, that code is used. Otherwise the code is `VALIDATION_ERROR`.
- A malformed JSON body gives `VALIDATION_ERROR` with the message `"Request body is not valid JSON"`.
